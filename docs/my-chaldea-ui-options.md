# 所持・育成管理 UI設計記録

更新日: 2026-08-24  
状態: Approved  
承認日: 2026-08-24  
参照デモ: `docs/my-chaldea-ui-comparison.html`

## 承認済みの結論

当初の「スプレッドシート型」「コンパクト行型」「育成ボード型」は採用せず、所持・育成管理の主画面を「横長一覧＋詳細」として確定する。

- 一覧＋詳細: 承認済みの主画面。PC／SPとも横長リストとし、現在値／目標値の詳細編集を組み合わせる
- スプレッドシート: MVPの承認済みベースラインには含めない。連続編集の必要性を実利用で確認後に再検討する
- 所持登録カタログ: NP0による未所持表現をAへ統合したため、独立モードにはしない比較対象
- 育成ボード: 状況把握に使う補助ビュー候補。MVPの主画面にはしない

PCは左に横長一覧、右に選択中の詳細を置く。SPは横長一覧から詳細サブページへ進む。同じ情報順序と入力コンポーネントを使い、SPへ一括編集表を縮小して持ち込まない。右詳細は未選択時には閉じ、再訪時の選択復元は利用者テスト後に判断する。

## 保存モデル

明示的な「保存」ボタンは設けない。

- セレクト、チェック、トグルは変更直後にローカル保存する。
- 数値入力は妥当な値になった時点、またはblur時に保存する。入力途中の不正値は保存しない。
- 表示状態は「保存中」「端末に保存済み」「保存失敗」を区別する。クラウド同期を示す状態は設けない。
- 直近の単一変更と所持一括変更にはUndoを提供する。
- 自動保存中に画面を移動しても入力を失わない。失敗時は該当項目と再試行操作を示す。

所持・育成管理はデータ管理そのものを目的とし、ダメージ計算への遷移を主操作にしない。保存値は他機能から自然に参照されるが、この画面内で計算利用を促進しない。

## 所持状態と宝具レベル

所持状態を独立した真偽値として操作させず、FGO Lab上では宝具Lvから導出する。

- 宝具Lv 0: 未所持
- 宝具Lv 1〜5: 所持
- 宝具Lv不明: インポート確認中だけに存在する一時状態。0として保存しない

NP0はゲーム内の宝具レベルではなく、FGO Labの管理用表示であることを初回説明と入力ラベルで示す。0へ変更してもレベルやスキル等の入力済み値は即時削除せず非アクティブにし、Undoで戻せるようにする。再び1以上へ変更した場合は以前の値を復元し、必要に応じて「要確認」を表示する。

これによりAの「選択・編集／所持登録」モード切替は不要になる。ただしAの左側へ宝具Lv入力は置かない。画像・名称は詳細を開く操作に限定し、宝具Lv 0〜5の変更は右詳細、SPでは詳細サブページへ集約する。

初回プロフィールでは全サーヴァントのユーザーレコードを事前作成せず、マスターデータの全サーヴァントを `NP0 = 未所持` として一覧表示する。初期表示は `全サーヴァント` とし、`所持のみ` と `未所持のみ` へ切り替えられる。所持のみが0件の場合も空の画面にはせず、未登録であることと全件表示へ戻る方法が分かる空状態を表示する。

未所持かつ保存履歴のないサーヴァントを初めて開いた場合は、Lv1、再臨0、スキル1/1/1を編集開始値として見せるが、値を変更するまでユーザーレコードは作らない。一度所持登録したサーヴァントをNP0へ戻した場合は、以前の育成値を非アクティブ状態で保持する。これにより初回状態と所持解除後の復元を区別する。マスターデータへ追加された新規サーヴァントも、アプリ更新後に未所持として自動的に全件表示へ加わる。

A左側の責務は、検索、絞り込み、所持状態と主要育成値の確認、編集対象の選択だけとする。複数騎を連続編集する必要がある場合はBへ切り替え、A左側を簡易編集表にしない。

### A右側の編集方針

Chaldea.centerのサーヴァント詳細から、セクション見出しとアイコン付き行を縦に並べる編集リズムを参照する。ただし機能一式は移植せず、保有・育成状態の管理に必要なものだけへ絞る。

- 右側上部は `現在値` と `育成目標` の2タブとする。PCの右ペインとSPの詳細画面で同じ構造を使う。
- 現在値タブは、サーヴァントLv、霊基再臨、宝具Lv、保有スキルLvを縦に配置する。
- スキルはDBに登録されたアイコンと名称を表示し、どのスキルを編集しているか画像でも識別できるようにする。
- 育成目標タブは現在値と目標値を同じ行で示す。ただしChaldea.centerのように両値を全画面で常時併記せず、目標設定時だけ差分を見せる。
- 必要素材は現在値から目標値までの強化経路をDBから集計し、目標タブ内で確認する。ここで示すのは必要総数であり、利用者の所持素材を差し引いた不足数ではない。
- 必要素材は件数を省略せず、対象となる全素材を用途別に縦表示する。`ほかN種`、上位数件だけの表示、別ページへの退避は行わない。
- 種火はレアリティ、クラス一致、成功ボーナス、投入単位で必要数とQPが変わるため、採用した計算条件を素材一覧の直下へ常時表示する。
- 素材計算に必要なため霊基再臨段階を管理対象へ加える。宝具Lvは記録するが、素材計算の目標項目には含めない。
- スキル効果詳細、宝具効果詳細、プロフィール、イラスト、音声、クエスト、コマンドコードなどの閲覧ページは作らない。
- 現在値タブと育成目標タブの上部に、`Lv90`、`Lv100`、`Lv120`、`スキル全て10` のショートカットを一列で置く。各入力行へ同じボタンを繰り返さず、頻出操作を一か所へ集約する。
- ショートカットは値を即時反映して自動保存し、通常入力と同様にUndoできる。未所持状態でレベルやスキルだけを変更しても所持にはせず、所持判定は宝具Lv 1以上だけで行う。

### A左側の表示方針

A左側はPC／SPとも横長リストを採用する。

- 顔画像、名称、クラス、現在Lv、宝具Lv、スキル要約を一行で表示する。
- PCでは左一覧と右詳細を並べる。SPでも同じ行構造を使い、選択後に詳細画面へ遷移する。
- 一覧は確認と選択に限定し、宝具Lvを含む編集UIを置かない。
- 未所持は顔画像を弱め、値欄へ `NP0 / 未所持` と表示する。所持中の行と同じ高さを維持する。
- 顔グリッドとの表示切り替えは設けない。表示方式の選択を利用者へ委ねず、検索・絞り込み・対象選択へ集中させる。

顔グリッドは一覧性に優れる一方、名称や育成状態を知るために詳細を開く回数が増える。保有管理ではキャラクターの発見速度だけでなく現在値の確認も頻出するため、表示件数より一行で判断できることを優先する。

## 比較するタスク

1. 未所持から所持へ素早く登録する。
2. レベル、宝具レベル、スキルを日常的に更新する。
3. 複数騎の同じ項目を連続編集する。
4. 現在値と目標値の差を確認する。
5. 未入力や推定値を見つける。
6. その状態をダメージ計算で即座に使う。
7. 320px幅でも主要な更新を完了する。

## 四パターンの位置付け

| パターン | 強いタスク | 弱いタスク | 現時点の位置付け |
|---|---|---|---|
| A. 一覧＋詳細 | 所持の俯瞰、日常更新、確認、モバイル | 大量の同一項目編集 | 採用。PC／SPとも横長リスト |
| B. 編集シート | PCでの連続編集、比較 | モバイル、項目説明 | MVPでは不採用。将来再検討 |
| C. 所持登録カタログ | 初回登録、追加実装分の確認 | 詳細育成値の編集 | Aへ統合し、独立採用しない |
| D. 育成ボード | 育成状況の俯瞰、再発見 | 正確な値の編集、一覧密度 | Phase 2以降の補助候補 |

## 確定後も検証すること

- 右詳細のNP0＝未所持が初見でも理解でき、別の所持チェックより入力が速いか。
- Dが育成判断へ実際に寄与するか。単なるカード整理なら採用しない。
- サーヴァントと概念礼装を同じ操作モデルにするか、上位タブだけ共有して編集項目は分けるか。

デモ値と画像は操作比較用であり、仕様値ではない。承認済みの実装基準は `docs/ui-design-spec.md` と `docs/implementation-plan.md` を正とする。

## 参照UIから採用する考え方

- Chaldea: 一覧で検索・クラス絞り込み・育成値要約を行い、詳細で現在値と目標値を並べて編集する。
- GameWith所有率チェッカー: 多数の画像を同時に見せ、所持状態と件数を即時に把握する。
- FGO Lab: PCでは左に横長一覧、右に詳細編集を置く。SPでは最初に一覧だけを表示し、サーヴァント選択後に詳細へ切り替え、明示的な「一覧へ戻る」を表示する。

画像・名称は詳細を開くだけにする。A左側には編集UIを置かず、タップ対象の意味を固定する。
