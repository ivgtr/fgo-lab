# ADR-008: 現行要件へ収束させるリファクタリング契約

- Status: accepted
- Date: 2026-08-24

> 作業は既存実装との後方互換性を目的とした複雑化は避け、現在の要件に対して最適な実装を優先し、必要であれば破壊的変更や旧実装の削除も許容し、新旧の実装を併存させず、最終的に破綻しにくい構造へ収束させる。

リファクタリングでは、既存実装との後方互換性を目的とした複雑化を避け、現在の要件に対して最適な実装を優先する。必要なら破壊的変更と旧実装の削除を行い、新旧のAPI、状態、処理経路、互換フラグを併存させない。変更前に現行の利用箇所と維持すべき動作を確認し、完了時には一つの実装へ収束させる。

新しいファイル、型、interface、クラス、Hook、Store、Service、ラッパーは、変更理由の独立、依存方向の単純化、状態所有の明確化、副作用の隔離、重複の統合、公開APIの縮小、テスト境界のいずれかを説明できる場合だけ追加する。ファイル数や形式的な層ではなく、変更理由、データフロー、状態所有、副作用、削除可能性を評価する。

破壊的変更を行う場合はschemaまたはengine versionを更新し、変更対象、理由、更新した利用箇所、削除した旧経路を記録する。利用されていない旧APIをdeprecatedとして残さず、旧形式の計算結果を現行結果へ暗黙変換しない。

永続化schemaの更新では、現行形式へ安全に写せるユーザーデータだけを一方向に移行し、正しさを保証できない計算draftと履歴は破棄する。移行結果は直ちに現行schemaで保存し、旧形式と現行形式をランタイムで併存・同期させない。
