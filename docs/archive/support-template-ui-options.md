# 支援条件 UI設計記録

更新日: 2026-08-25

状態: UI設計案・レビュー待ち

参照デモ: `docs/support-template-ui-comparison.html`

優先する既存実装: 所持・育成管理の一覧＋詳細UI

## 結論

支援条件管理は、比較デモのB「支援元スタック」をページ全体として移植しない。本採用済みの所持・育成管理と同じ「左に一覧、右に詳細」の骨格を使い、選択した支援条件の詳細内へ支援元スタックを配置する。

- PC: 左に保存済み支援条件、右に選択中の編集内容を表示する。
- SP: 保存済み支援条件の一覧から詳細サブページへ進み、「一覧へ戻る」で復帰する。
- 一覧は検索、要約、選択に限定し、編集操作を置かない。
- 詳細は名称、支援元、スキル、適用効果の確認と編集を縦方向へ集約する。
- 妥当な変更は自動保存し、通常の保存ボタンは置かない。
- ダメージ計算での一時変更は保存済み支援条件へ暗黙反映しない。

これにより、所持・育成管理で本採用した情報密度、選択方法、レスポンシブ遷移、自動保存の考え方を揃える。デモBの「支援役から組み立てる」操作順と、デモCの「効果を確認する」機能は右詳細へ取り込む。

## 画面の目的

ダメージ計算と火力ランキングで再利用する支援条件を、DB上の支援役とスキルから作成・保存・編集する。FGOのパーティ配置を再現する編成画面ではないため、前衛／後衛の位置、Wave、礼装、交代順は管理しない。

主な利用タスクは次の四つとする。

1. 保存済み条件を名前や支援役から探して内容を確認する。
2. 支援役を追加し、使用するスキルとレベルを設定する。
3. 現在有効な効果と、その付与元を確認する。
4. 保存済み条件を計算へ呼び出し、必要なら計算内だけで一時変更する。

## デモから復元する機能

### 必須

- 支援条件の作成、名称変更、削除
- 条件名、支援役名、主要効果による検索
- 最終使用時刻と更新時刻を使った並び替え
- 支援元の追加、削除、自前／フレンド区分
- 同じサーヴァントを複数の支援元として追加
- 支援元ごとの全保有スキル表示
- スキルの使用中／未使用切り替えとLv変更
- 顔画像、スキル画像、名称、効果、対象、発動条件、デメリットの表示
- 支援元数、使用スキル数、効果種類別の概要
- 効果合計から付与元を確認する内訳
- 支援条件管理、ダメージ計算、ランキングで共用する検索ロジックと一覧行
- 計算画面へ呼び出した構成と保存元の分離

### 後続機能

- 概念礼装、魔術礼装、カスタム効果を同じ付与元契約へ追加
- 支援元の並べ替えと効果の発動順管理
- 保存済み条件を複製して別名保存
- マスターデータ更新後の差分確認

初回実装はサーヴァント由来の支援スキルを完成させる。付与元カテゴリを先に広げて、各カテゴリが不完全な状態になることは避ける。

## 現行実装との差分

現行画面でできるのは、条件の新規作成、セレクトボックスからの選択、支援役の追加、各スキルの使用切り替えとLv変更までである。次が実装漏れとして残っている。

| 領域 | 現状 | 必要な補完 |
|---|---|---|
| 条件一覧 | `select`で名前だけを表示 | 検索可能な横長一覧、構成要約、最終使用時刻 |
| 条件編集 | 自動生成名を見出し表示 | 名称編集、削除、複製、自動保存状態 |
| 支援元 | サーヴァントID単位で一度だけ追加 | 支援元インスタンス、自前／フレンド、同一役の複数追加、削除 |
| スキル | checkbox、Lv、文字列詳細 | 画像付き行、使用トグル、対象・条件・デメリット、値の要約 |
| 効果確認 | 個別スキルの説明のみ | 効果種類別の合計、付与元内訳、対象外理由 |
| 共通利用 | 計算画面に別実装の検索モーダル | 管理・計算・ランキングで同じ一覧行と検索ロジックを共用 |
| 使用履歴 | `lastUsedAt`を表示・更新しない | 呼び出し成功時に更新し、一覧の検索・並び順へ反映 |

## レイアウト

### PC

所持・育成管理の `.master-detail` と同じ二ペイン構成を基準にする。

```text
┌ 保存済み支援条件 ─────────┬ 支援条件の詳細 ──────────────────┐
│ [名前・支援役・効果で検索] │ [条件名____________________]      │
│ [最近使用▼]      [新規作成] │ 3騎・使用8スキル・自動保存済み   │
│                            │                                  │
│ W光コヤン＋オベロン        │ 光のコヤンスカヤ 1   [自前▼]     │
│ 3騎・8スキル・今日使用     │  [スキル1] 使用中  Lv10          │
│                            │  [スキル2] 未使用  Lv10          │
│ キャストリア宝具支援       │  [スキル3] 使用中  Lv10          │
│ 2騎・4スキル・3日前使用    │                                  │
│                            │ オベロン             [フレンド▼] │
│                            │  ...                             │
│                            │                                  │
│                            │ [＋ 支援元を追加]                 │
│                            │ ▸ 適用効果の概要                  │
│                            │ [この支援条件を削除]              │
└────────────────────────────┴──────────────────────────────────┘
```

左ペインの責務は検索・並び替え・選択だけとする。行には最大3枚の顔画像、条件名、支援元数、使用スキル数、相対的な最終使用時刻を表示する。効果タグは検索には使うが、行の高さを不安定にする場合は主要2種類までに制限する。

右ペインは選択中の一条件だけを編集する。名称入力と保存状態を先頭に置き、次に支援元スタック、追加操作、効果概要、削除操作の順とする。効果概要を常時右側へ分離せず、狭いPC幅やSPでも同じ順序を保てる縦積みにする。

### SP

- 初期表示は保存済み条件の横長一覧とする。
- 行を選択すると同じ画面内の詳細状態へ進み、一覧を隠す。
- 詳細上部に「← 支援条件一覧へ戻る」を置く。
- 支援元カードとスキル行は一列で表示し、横スクロールさせない。
- 効果概要は支援元スタックの後ろへ置く折りたたみとする。
- 支援元追加と検索モーダルは下から開くシートとして表示する。
- 320px幅でもスキルの使用切り替えとLv変更を同時に操作できるよう、Lv入力だけを固定幅にする。

## 一覧の設計

一覧上部は所持・育成管理と同じ順序に揃える。

1. 検索入力
2. 「新しい支援条件」
3. 件数と並び順
4. 横長の条件一覧

検索対象は条件名、支援役名、主要効果名とする。並び順は「最近使用」「更新が新しい」「名前順」を用意し、既定は最近使用とする。未使用の新規条件は作成日時で並べる。

一覧行を選択しただけでは `lastUsedAt` を更新しない。ダメージ計算またはランキングへ実際に適用した時だけ最終使用として記録する。

空状態では説明だけを出さず、「新しい支援条件」を主操作として表示する。新規作成後は作成した条件を右詳細で選択し、条件名へフォーカスする。

## 詳細の設計

### 条件名と保存

- 新規作成時は一時名を自動採番し、詳細を開いた直後から名称を編集できる。
- 名称は妥当な値になったblur時に保存する。
- checkbox、select、トグルは変更直後に保存する。
- 保存状態は「保存中」「端末に保存済み」「保存に失敗」を表示する。
- 明示的な保存ボタンは置かない。
- 削除は確認ダイアログを経由し、完了後はUndoできるようにする。

### 支援元スタック

支援元はサーヴァントそのものではなく、テンプレート内の配置インスタンスとして扱う。同じサーヴァントを2騎追加しても、それぞれのスキル使用状態とLvを独立して保持する。

支援元の見出しには次を表示する。

- 顔画像と名称
- 同一サーヴァント内の補助番号（例: 光のコヤンスカヤ 1／2）
- 自前／フレンド
- 使用中のスキル数
- 支援元の削除操作

「自前」は所持・育成管理のスキルLvを初期値として参照できる。「フレンド」は独立したLvを保持する。参照後に個別変更しても、所持・育成管理の保存値は変更しない。

### スキル行

DB上の保有スキルを支援元ごとに全件表示し、削除ではなく使用中／未使用を切り替える。行の情報順は所持・育成管理のスキル行に揃える。

1. スキル画像
2. スキル名
3. 主要効果の短い要約
4. 使用トグル
5. Lv入力

対象、条件、デメリット、全効果は補足行または展開領域へ置く。内部識別子や検証状態をそのまま表示せず、「攻撃役へ適用」「対象の特性が一致した場合」のような利用者向け文言へ変換する。ダメージへ影響しない効果もスキル単位の文脈を壊さないよう表示する。

### 適用効果の概要

独立した台帳画面は作らず、詳細下部の「適用効果の概要」へ統合する。

- 攻撃力、カード性能、宝具威力、特攻など効果種類ごとの合計
- 合計を構成する支援元、スキル、個別値
- 条件一致時だけ適用される効果の件数
- 現在の攻撃対象では適用されない効果と利用者向け理由

支援条件管理には攻撃対象がないため、条件付き効果を無条件に合計へ含めない。「条件付き1件」のように分離する。具体的な適用結果は計算画面で攻撃対象と照合して表示する。

## 支援元追加

追加モーダルは既存の共通サーヴァント選択UIを使い、所持・育成管理と全サーヴァントDBを切り替えられるようにする。

- 所持から選ぶ場合は保存済みスキルLvを初期値にする。
- 全DBから選ぶ場合はLv10を初期値にし、追加後に変更できる。
- 選択後に自前／フレンドを確定して追加する。
- 既に存在するサーヴァントも候補から除外しない。
- 追加直後は全スキルを未使用として表示し、利用者が使うスキルを選ぶ。

## 共通の支援条件検索UI

検索ロジックと一覧行は共通コンポーネントにし、利用箇所に応じて置き場所と末尾の操作だけを変える。

- 管理画面: 左ペインへ埋め込み、行の選択で右詳細を開く
- ダメージ計算: 「この条件を使う」
- ランキング: 「共通条件に使う」

ダメージ計算とランキングでは共通コンポーネントをモーダル内へ置く。候補には条件名、顔画像、支援元数、使用スキル数、主要効果、最終使用時刻を表示する。選択前に構成を判別できることを優先し、`select`には戻さない。

## ダメージ計算での一時編集

保存済み条件を呼び出した後は、セット名だけで内容を隠さず、全支援元と全スキルを計算画面へ展開する。計算画面での変更は次の差分として扱う。

- 保存内容と同じ
- レベルや使用状態を変更
- 計算内で追加
- 計算内で削除予定

画面には内部状態名を露出せず、変更箇所へ `Lv10 → Lv9`、`この計算で追加`、`取り消す` のような具体的な文言を近接表示する。

「元の条件に戻す」「変更をこの支援条件へ反映」「現在の構成を新しい支援条件として保存」を全件一覧の後ろに置く。単なる呼び出しや一時変更では保存元を書き換えない。

## 保存モデルの補完

支援元自体の属性や同一サーヴァントの複数配置を表現するため、概念的には次の構造を使う。

```text
SupportTemplate
├─ templateId / name / updatedAt / lastUsedAt / masterDataVersion
└─ sources[]
   ├─ sourceInstanceId
   ├─ sourceType
   ├─ sourceId
   ├─ ownership: owned | friend | virtual
   ├─ order
   └─ skills[]
      ├─ skillId
      ├─ skillLevel
      ├─ enabled
      └─ order
```

効果値、名称、画像、対象条件は保存せず、利用時にマスターデータから再解決する。実ストレージでは既存データとの後方互換を優先し、`effects[]` の各行へ `sourceInstanceId` と `ownership` を正規化して保持する。旧行は読み込み時に `sourceType` と `sourceId`から同じ支援元インスタンスへ自動集約するため、schema versionを上げずに既存データを維持できる。

## 実装順

1. 支援元インスタンスを持つschemaとprofile-domain操作、既存データmigration
2. 一覧＋詳細シェル、SPの一覧→詳細遷移、名称編集、削除、自動保存
3. 支援元追加・削除、自前／フレンド、同一役の複数追加
4. 画像付きスキル行、使用切り替え、Lv編集、説明表示
5. 効果種類別の概要と付与元内訳
6. 共通検索UIを管理の左ペインと計算・ランキングのモーダルへ接続
7. 計算内の一時差分、復元、保存元への明示反映、別名保存

各段階でPC、390px、320px、キーボード、再読み込み、自動保存失敗、Undoを確認する。

## 採用しないもの

- デモBの作成専用ページを主画面にすること
- 効果別台帳を独立した上位画面にすること
- 保存済み条件を`select`だけで選ばせること
- 一覧行へ編集フォームを詰め込むこと
- SPへPC二ペインを縮小して表示すること
- 支援条件へ編成位置、Wave、礼装を混在させること
- 内部の識別子、精度区分、未解決コードを利用者向けUIへそのまま表示すること
